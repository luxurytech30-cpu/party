# Production deployment

The web app runs on Vercel and the Express API runs on Render. MongoDB remains on Atlas.

## 1. Render API

Push the repository to an account connected to Render, then create a Blueprint from the root `render.yaml`.

- The Blueprint builds the shared workspace before the API, starts the compiled server, and checks `/health`.
- `MONGODB_URI`: the Atlas connection string for the intended database. Never use `memory` in production.
- `JWT_ACCESS_SECRET`: generated by Render. Do not use a development secret.
- `CORS_ORIGINS`: the exact Vercel production origin (and any custom domain), comma-separated.
- Optional media uploads: set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` in Render.
- Do not configure `DEV_ADMIN_PASSWORD` in production. Existing database users remain available.

Verify the Render `/health` response reports `status: ok` and `db: up`.

## 2. Vercel web app

Import the same repository with **Root Directory `apps/web`**. Enable source files outside the root directory for shared workspace imports. The local `vercel.json` sets the workspace installation and build commands.

Set `API_URL` to the Render HTTPS origin, without `/api/v1`, before building. The app proxies `/api/v1/*` to this backend. Update `CORS_ORIGINS` on Render once the Vercel production origin is assigned.

Development may use `http://localhost:4001`. Production builds require an explicit HTTPS `API_URL`, so a successful frontend deployment cannot silently point visitors to localhost.

## 3. Verification

- Open `/ar`, `/he`, and `/en` and check that the Next.js development indicator is absent.
- Call `/api/v1/categories` and `/api/v1/public/businesses` through the Vercel origin.
- Check guest gift discovery and host planning, including multiple services in the same category.
- Check sign-in and refresh through the same-origin proxy.

No production deployment URL exists until both hosting services have been created and their deployments have succeeded.
